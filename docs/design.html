yeet — plan-before-apply, zero-downtime deploys for compose-first apps

An agentless, single-binary deploy engine for apps described by a docker-compose file: preview every deploy as a rendered diff and an exact command list, then release with health-gated zero downtime — keeping your own proxy, database, and conventions. Plan/apply discipline for app releases, honest about where imperative deploys can and cannot be planned.

01 / Positioning

The wedge: plan/apply + zero-downtime for compose apps

The single-server deploy niche is busy — Kamal 2, Sidekick, Haloy, Uncloud, Dokploy, Coolify. Two capabilities remain unclaimed together:

  • Plan before apply. No tool in this category shows you — before touching a host — the rendered artifacts, the pinned images, and the exact remote command list, then binds that plan to the apply.
  • Zero-downtime for docker-compose apps as they are. Coolify explicitly can't do ZDD for compose resources; Kamal is image/role-centric, not compose-native; Uncloud is closest but self-describes as not production-ready.

One-line positioning

Zero-downtime deploys for docker-compose apps: agentless, plan-before-apply, keep your proxy. Checkable in a 90-second demo (with a prebuilt image — a cold build blows the budget, and we say so). ("yeet" is a working codename — the release gets a searchable, non-slang name.)

What "plan" honestly means here (rev 4)

Deploys are imperative, so this is not a full Terraform plan and the doc no longer implies one. yeet plan gives: (a) rendered files diffed against the live release — high fidelity; (b) image binding — digest-pinned when CI built the image (prebuilt mode, the recommended path), or bound to git SHA + build-context hash in local-build mode with the digest recorded at apply; (c) the command list with runtime branches shown as branches (health-gate outcomes, the rollback path); (d) hooks shown verbatim as commands — their effects are explicitly unplannable. Fidelity ranking: config > images > choreography > hooks. Closer to terraform plan for config/images and make -n for hooks — stated, not hidden.

Not positioned against BYO-proxy: Kamal 2 allows keeping Traefik (proxy: false + an official guide) — that's table stakes. yeet's difference is compose-nativeness, plan/apply, and journaled/fenced deploy state. It ships as an extraction from a production pipeline, not a platform.

02 / Principles & non-goals

What it commits to — and what it refuses to be

Design principles

  • Agentless. Nothing on hosts but a container runtime and SSH. No control plane to run or upgrade.
  • Your compose file is the contract; yeet renders the deployable. (Reworded in rev 4 — "source of truth" overclaimed.) The user's docker-compose.yml is the authoritative input: yeet renders a per-release derivative into releases/<id>/, injecting only a declared, closed set of things — scale, its own namespaced labels, the generated healthcheck, env-file paths. yeet render shows the exact delta between your file and what runs. Anything yeet cannot express is still expressible in your compose file, because that file remains the base. (Rev 5) Rendering canonicalizes through docker compose config: anchors, extends, multiple -f files, profiles, includes and interpolation are resolved by compose itself, never re-implemented — the supported dialect is exactly what compose accepts, and both render and plan diff canonical forms, so a parser gap cannot silently diverge from what up would read.
  • Plan before apply — with the fidelity contract stated in §01. The plan artifact binds to the apply; drift is measured over a defined set (live release id, running-image digests, config hash — not all of docker inspect, which would false-positive on every restart).
  • Mechanisms, not claims. Resumability = a per-host journal; exclusivity = a fenced lock; rollback = versioned releases with pinned retention (§05–06).
  • YAML outside, CUE inside. Users write YAML; an embedded CUE schema validates it; the engine re-words CUE errors into plain, located messages. CUE never reaches the user.
  • Boring and legible. Everything it does you could do by hand over SSH; --verbose shows the commands.

Explicit non-goals

  • not a Kubernetes replacement — no scheduler, no cluster control loop.
  • not a CI system — it is invoked by CI or a laptop.
  • not config management — host prep is minimal and idempotent.
  • not a backup tool — data safety runs through hooks (Backup plane cut in rev 2 as a monk-ism).
  • not a plugin platform on day one — curated compiled-in providers + a command escape hatch; public extension points only after ≥3 real apps (rule of three).
  • not multi-host in v1 — the state/lock protocol is designed for host sets (§05) but v1 executes single-host only. Multi-host lands at M3 with real fleet users. (Rev 4: this halves the v1 surface the maintenance-economics risk pointed at.)
03 / Architecture & the service model

A small core, three service classes, an owned proxy story

The core owns config, planning, SSH transport, state/journal/lock, and the lifecycle. Strategy, proxy, and runtime are a coupled triple — admitted, not abstracted away — so v1 ships one release engine (the production-proven compose choreography) rather than a public Strategy interface.

Three service classes — every compose service has exactly one

  • Roles — released by the choreography. Each maps to a compose service (with its own image; a top-level image: is only a default for single-image apps — rev 4 fix: per-service images are the normal compose shape).
  • Accessories — stateful deps (postgres, redis). Converged only by yeet accessory apply (a planned, explicit maintenance event: shows the diff, refuses destructive volume changes without --force). Never touched mid-deploy: all release-phase and job compose invocations run --no-deps, so a depends_on can never silently recreate a database. Preflight asserts declared accessories are running and healthy before any deploy proceeds — "healthy" requires the accessory to define a healthcheck, and validate warns when the assertion degrades to running-only. Accessories are optional: an app on RDS or any external service simply declares none.
  • Jobs — run-once services (migrate). Executed by hooks with --no-deps; they are neither rolled nor converged. (Rev 4: migrate previously had no class — this closes the hole where it pierced the accessory firewall.)

(Rev 5 — corpus-tested against 17 in-house compose projects.) Two corollaries: (1) An all-accessory app (an infra stack — proxy, db, dashboards) is legal: zero roles; deploy reduces to transfer + preflight and accessory apply does the work. (2) yeet init is a doctor, not just a scaffold: it classifies every service (proxy → accessory or external, db/queue → accessory, one-shot → job, the rest → roles) and prints the exact compose delta each role needs before it can roll — "drop container_name", "unbind host port 8080; the proxy routes instead". In the survey nearly every project sat a 3–5 line diff from rolling; printing that diff is what makes "works on your compose file" true in practice, not just on paper. The generality claim, stated precisely: universal deployability (every service can at least recreate), conditional zero-downtime (each role earns rolling by meeting preconditions that are physics — two containers cannot share a host port — not tool policy).

The release mechanism — named, with constraints

Scale–health–drain: docker compose up -d --scale svc=2 --no-recreate --no-deps with the new image → wait for the generated healthcheck → proxy shifts to healthy endpoints → SIGTERM + grace drain → remove old. Production-proven (docker-rollout). yeet validate enforces its preconditions: no container_name, no host-port bindings, no deploy.replicas on rolled services; and it warns on rw named volumes/binds shared by a rolled service — during overlap two writers exist briefly, so mounts must be overlap-safe (documented, warned, not silently assumed). During overlap the proxy balances across old+new — mixed-version serving is a stated behavior, and the reason additive-first migrations are required.

The traffic shift is a protocol, not an arrow

(Rev 5 — "proxy shifts to healthy endpoints" was the one unexamined step in the choreography, and it is exactly where zero-downtime is won or lost: stopping the old container races the proxy's view of it, and the loser is a burst of 502s mid-demo.) Every proxy provider implements three operations: join (the new container becomes routable via its healthcheck), drain (the old container is removed from routing before it is signalled — for traefik-docker, by poisoning its health state so the provider drops it), and converged (a bounded wait for the proxy to observe the change). The sequence is join → converged → drain → converged → drain.wait connection bleed → SIGTERM → grace → remove; SIGTERM never races the proxy. The command provider maps the same three operations onto user-supplied commands — the protocol is proxy-agnostic, which is what keeps the Caddy/nginx path first-class. drain: is therefore valid on rolling roles too: WebSocket/SSE apps set a long bleed window, and in-flight connections ending at its expiry is stated behavior, not a surprise. Two general preconditions ride along: sessionful apps need sticky sessions (or version-skew tolerance) during overlap, and rolling assumes overlap-capable resources — a role holding an exclusive resource (a GPU device reservation, an exclusive volume) cannot run two copies, so validate warns on device requests for rolled roles; recreate is the exclusive-resource mode.

Readiness has one owner — and one compilation rule

(Rev 4 — the previous text answered this both ways.) The role's ready: contract is the single authoritative definition. Rules: (1) http and exec kinds compile into the container healthcheck — which is what both the proxy and the release engine gate on. (2) log and heartbeat kinds cannot gate a proxy (they aren't periodic probes); they are release-engine wait conditions + verify checks, valid only on non-proxied roles — validate enforces that a rolled, proxied role has an http/exec contract. (3) If the compose service already defines a healthcheck: no ready: → it is adopted as the contract; both present → the generated one wins with a validate warning. One definition, three consumers, no ambiguity.

The proxy is owned — managed or external, never assumed

(Rev 4 — previously the proxy's own lifecycle was nobody's job and the fresh-VPS story died at step zero.) proxy.managed: true: yeet bootstrap deploys Traefik itself — container, the shared docker network, ACME storage volume — and yeet proxy apply converges it thereafter (same explicit-maintenance semantics as accessories). managed: false: you own it; preflight verifies it is present and routing. Label injection is namespaced (yeet.*-generated router/service names), user-authored labels pass through untouched, and a router-name collision is a validate error. (Rev 5) The managed proxy is host-scoped, not app-scoped: several yeet apps on one host share one Traefik — the first bootstrap creates it, any app's proxy apply converges it, and two apps declaring managed: true with divergent proxy config is a preflight conflict, not a last-writer-wins race. A third, common shape — the proxy defined inside the compose file (5 of the 17 surveyed projects) — is first-class: declare it an accessory (converged by accessory apply, never touched mid-deploy) with managed: false; preflight's present-and-routing check targets that container, and validate checks its docker provider is enabled — label routing depends on it.

First contact with a fresh host

yeet bootstrap = provision (runtime, deploy user, dirs, restart policies) + registry login + proxy apply (if managed) + accessory apply. After bootstrap, every deploy is a pure release. yeet deploy on an un-bootstrapped host fails preflight with exactly that instruction — the demo story is init → bootstrap → deploy, honestly three commands, not one.

04 / The deploy lifecycle

One pipeline, a per-role DAG inside release

preflight
Validate + refresh + assert. Schema and rollability checks, secret resolution, SSH/registry reachability, disk headroom (including incoming image size), accessories running & healthy, proxy present & routing. Host-state refresh that the plan binds to. nothing mutates
build · push
Prebuilt mode (recommended): CI built it; the plan pinned its digest. Local-build mode: buildx with BuildKit --secret mounts; plan bound to git SHA + context hash, digest recorded at apply. (Rev 5) Image transport is declared, not assumed: registry push/pull (default) or transport: archive — docker save | ssh docker load — for registry-free and air-gapped hosts. Multi-arch via buildx --platform; a digest pin on a manifest list covers every architecture in it. hook: pre_build, post_build
transfer
Ship the versioned release dir — releases/<id>/: rendered compose, env, secrets (mode 600), artifacts, and the yeet.yml snapshot (modes, order — so rollback/abort replay the old choreography with the old config, explicitly). Nothing live is overwritten. hook: pre_transfer
pre-release
Jobs (migrations), journaled with a result protocol (§06). Run with --no-deps against accessories preflight already proved alive. hook: migrate
release
Per-role DAG, journaled per sub-step. mode: rolling | recreate (rev 4: stop-start deleted — it was an undefined synonym of recreate) plus an optional drain block — drain: { signal: TSTP, wait: 30s } — a real schema field, not prose (sent to the old container before stop; how Sidekiq/Taskiq-style workers finish in-flight jobs). Valid on any mode — on rolling roles it is the connection-bleed window after the proxy drain (§03). monk: scheduler (recreate, singleton) → web (rolling) → worker (recreate + drain). Activation = symlink flip. hook: pre_release, post_release
verify
All roles, host-side. "Host-local" defined precisely (rev 4): probes execute on the host against the container network — docker exec or a curl to the container's network address — never through the edge, which is also how this coexists with the no-host-ports rule. Heartbeat checks likewise run via docker exec into the accessory (no runner→Redis credentials — stays agentless). Edge probes are advisory. Then the soak window. hook: verify
finalize
Teardown + prune with pinned retention (last N releases + images never pruned; rollback never pulls). Record state, release the lock. hook: post_deploy

Canary remains deliberately absent — an iterative shift-verify loop doesn't fit a linear pipeline honestly. Deferred, not faked.

05 / State, locking & partial failure

The mechanisms, now concretely specified

The journal — a spec, not a noun

(Rev 4.) Append-only JSONL at /var/lib/yeet/<app>/journal/<deploy-id>.jsonl, one fsync per record. Records: {deploy_id, epoch, phase, sub_step, role, intent|result, ts, operator, git_sha, config_hash}. GC is tied to the pinned-retention window (a journal outlives its release). yeet audit reads journals over SSH — including runs whose terminal scrolled away.

Fencing that works on every host

(Rev 4 — previously only the lock-authority host could validate epochs.) At deploy start the runner appends a deploy-start record (id, epoch, config hash) to every target host's journal. Every mutating command is wrapped host-side with a check against that host's own journal tail — a zombie runner is rejected locally, no cross-host call.

The lock — and what happens when its host is down

One explicit lock_authority host; lock record carries {owner, epoch, git SHA, config hash}; TTL on the host's clock with heartbeat renewal; breaking requires --force and prints the previous holder's journal tail. (Rev 4) Authority unreachable → deploys refuse — the safe default, stated. Break-glass: --lock-authority <other-host> requires an explicit operator acknowledgment and is journaled as such. Single-host apps (all of v1): the only host is the authority; the SPOF concern collapses.

One regime for every mutation

(Rev 5) deploy is not special: every mutating verb — rollback, resume, abort, secrets push, accessory apply, proxy apply, destroy — acquires the same lock, writes the same journal, and is fenced the same way. secrets push racing a deploy is a lock conflict, not an incident. One honesty note on fencing itself: the per-command journal-tail check is check-then-act, not atomic — the residual window between check and command is accepted and stated, and the journal makes any loser forensically visible.

Multi-host semantics — designed now, executed at M3

Fan-out policies (fail-fast default: stop on first host failure, leave successes, report divergence loudly; all-or-rollback: revert successes). "Previous release" is per-host unambiguous via each journal. yeet status diffs desired / recorded / actual — divergence is the point. v1 ships the protocol with a single-host executor; the fleet executor lands at M3 with real multi-host users.

Day-2

  • Reboot: restart policies bring everything back without yeet; singletons enforced by single-container mode.
  • Environments: (rev 4) environments: overlays in yeet.yml (yeet -e staging deploy) — different hosts/env per environment, same schema. No separate config dialect.
  • Leaving: (rev 4) yeet destroy (torn down with typed confirmation) and — with multi-host at M3 — yeet host retire so removed hosts don't strand orphaned containers that only status divergence would ever mention.
  • Certificates: each proxy provider declares renewal ownership (traefik-managed: itself; external: you) and status surfaces cert expiry.
06 / Rollback — scoped honestly

What is invertible, what is forward-only, and the migration gate protocol

ThingRollback semantics
App containersDeterministic. Previous release dir (image pinned locally) re-activated; the release dir's own yeet.yml snapshot drives the choreography — old release, old config, old modes.
ArtifactsDeterministic — versioned under releases/<id>/, symlink-activated, never overwritten.
Config & secretsDeterministic per release — rendered config + secrets content-hash recorded (hash in state for audit, content never logged). (Rev 5) Deterministic cuts both ways: rollback compares the target release's secrets hash against current and warns on mismatch — restoring rotated (possibly revoked) credentials is a stated choice, not an accident; --current-secrets re-renders today's secrets into the old release instead.
MigrationsForward-only. Expand/contract discipline; the contract step is the post_release hook.
AccessoriesOut of scope — maintenance events via accessory apply with their own plan.

The migration gate — now with a detection protocol (rev 4)

The gate's trigger was underspecified ("the journal shows the migrate hook applied changes" — an exit code can't say that). The protocol: yeet exports $YEET_RESULT_FILE to the migrate hook. A hook that writes changed=false declares a no-op → the gate stays open (auto-rollback permitted). Anything else — including writing nothing — fails safe: the deploy is treated as having applied schema changes, and on failed verify yeet halts-and-pages instead of auto-rolling back, unless the config asserts migrations: expand-only (the operator's informed promise that old code tolerates the new schema). Documented adapter snippets make alembic/rails/prisma report the flag correctly. The same gate governs yeet abort — aborting mid-deploy after a migration ran is the same hazard as auto-rollback (rev 4: previously only auto-rollback was gated). --no-rollback exists for operators who want failures to stand still; verify probes are host-side (§04) so an edge blip can't roll back a healthy release.

07 / Configuration

YAML you write, CUE that checks it

# yeet.yml — beside docker-compose.yml (the contract; yeet renders the deployable per release)
app: monk
compose: docker-compose.yaml
environments:
  production: { hosts: [monk.labstack.net], lock_authority: monk.labstack.net }
  staging:    { hosts: [staging.labstack.net] }

roles:                                # images come from the compose services;
  web:      { service: server,    mode: rolling,  ready: { http: /healthz } }
  worker:   { service: worker,    mode: recreate, drain: { signal: TERM, wait: 30s },
              ready: { heartbeat: "worker:alive<30s", via: redis } }   # checked via docker exec
  scheduler:{ service: scheduler, mode: recreate, singleton: true,
              ready: { log: "scheduler started", within: 30s } }
order: [scheduler, web, worker]

accessories: [postgres, redis]        # preflight asserts alive; converged only by `accessory apply`
jobs: [migrate]                       # run-once; invoked by hooks with --no-deps
artifacts: [{ from: web/dist, name: web }]
hooks: { migrate: docker compose run --rm --no-deps migrate }
migrations: expand-only               # informed promise; enables auto-rollback past the gate
verify:
  - { http: /healthz, role: web }     # host-side, via the container network — authoritative
  - { url: "https://monk.trade/", contains: 'id="root"', advisory: true }
secrets: { sops: secrets.enc.yaml }
proxy: { kind: traefik-docker, managed: false }   # monk brings its own; `managed: true` = yeet bootstraps it

Both config and state carry apiVersion; the engine refuses newer state and migrates older. secrets push re-renders per-role env, diffs the rendered output per role, and bounces only roles whose rendered env changed — that is the mechanism, not magic. (Rev 5) Every ready: kind takes timing knobs (within, start_period, interval) — slow starters (JVM warm-up, model loading) tune the gate rather than fight it.

10 / Generality audit

Is this curve-fitted to monk? A piece-by-piece answer

Extracted from one production app, so overfitting is the default unless actively resisted. (Rev 5) The generality boundary is itself explicit: anything describable as a docker-compose application — not VMs, not serverless, not Kubernetes manifests. Within that boundary, nothing structural may assume monk's shape; outside it, generality is a non-goal, not a failure. Element-by-element:

ElementClassWhy
plan/apply · journal · fencing · locks · versioned releases · auditagnosticPure deploy mechanics; would exist identically without monk.
scale–health–drainagnosticConvergent evolution — Kamal, Uncloud, docker-rollout arrived at the same choreography independently.
migration gateagnosticUniversal to DB-backed apps.
compose-native · docker · traefik-firstmarket choiceDeliberate segment narrowing (the wedge), not curve-fitting. command proxy is the Caddy/nginx path.
per-role modes + ordering + drainmonk-derived, generalizesweb+worker+scheduler is the generic shape — Rails/Sidekiq/cron, Django/Celery/beat, Node/BullMQ are isomorphic.
single top-level imagewas a monk fingerprint — fixed(Rev 4, caught by fresh-eyes review.) Roles now take images from their compose services; one-image apps set a default. The audit itself had missed its headline overfit.
artifacts (SPA-on-volume)quarantinedMonk's web-decoupling trick — optional extension, no core dependency.
heartbeat readinessquarantinedOne kind among http | exec | log | heartbeat, never privileged, non-proxied roles only.

Paper personas

  • Rails + Sidekiq + cron: web rolls on /up; sidekiq recreate with drain: {signal: TSTP, wait: 30s} — now a real schema field; cron singleton; rails db:migrate behind the gate. Clean fit.
  • Static site + Go API: API rolls; the site is an nginx/caddy service that also rolls; never touches artifacts. Clean fit.
  • PHP-FPM + nginx coupled pair: must move atomically; compose has no pod concept — and PHP is too large a share of the compose world to file under alien. (Rev 5) The schema seam is reserved now: a role maps to one or more compose services (services: [nginx, fpm]), the DAG node is the role, and co-rolled choreography (scale both → both healthy → shift → drain both) is specified at the design level. v1 validate still enforces one service per rolled role — execution stays gated on a real app (M3.5 candidate) — but generalizing later is additive, not rework.
  • Headless consumer fleet (Kafka/AMQP workers, a bot — no HTTP anywhere): proxy: none; roles roll or recreate with drain; readiness via exec/heartbeat; verify runs docker exec probes. The proxy is optional equipment, not a load-bearing assumption. Clean fit.
  • Raw-TCP/UDP service on a bound host port (mail, DNS, game server): host ports are forbidden only on rolled roles — such a role uses recreate and takes a stated brief gap (or Traefik's TCP/UDP routers where they fit). Honest fit: brief downtime, declared.

Anti-overfit rules

  • M3 exit: two apps, zero app-specific engine code — with the engine changing where it fought app #2. Frictionless onboarding of app #2 is a red flag (too monk-like to test anything).
  • Alien-validator rule (M3.5): the third app must be out-of-distribution — not Python, not SPA+API.
  • Quarantine discipline: monk-flavored features stay optional with no core dependencies; anything cut for being "our habit masquerading as a general concern" gets recorded (Backup plane, rev 2; single-image schema, rev 4).

12 / Roadmap — with exit criteria

Extraction first, generality earned

M0 · spike
Core lifecycle + SSH + compose runtime + scale–health–drain + traefik-docker (external mode). Exit: monk deploys end-to-end, zero-downtime, from the new binary.
M1 · plan/apply
YAML + embedded CUE validation, plan with refresh + binding + the fidelity contract in its output, render, bootstrap. Exit: yeet.sh fully retired for monk.
M2 · trustworthy
Journal (as specified in §05), fencing on every host, lock authority, resume/abort, the migration-gate protocol, per-role verify incl. drain, pinned retention, audit. Exit = the ops scenarios: kill the runner mid-release → resume recovers; fail verify after a migration → halt-and-page, not rollback; break a worker → verify catches it.
M3 · second app
Onboard unlock/justwatch. The fleet executor stays deferred — the protocol (§05) is designed, but no real multi-host need exists yet, and building it speculatively is exactly the maintenance-economics trap §11 warns about; single-host is a deliberate boundary until a real fleet user appears. Exit: two apps, zero app-specific engine code, engine changed where it fought app #2.
M3.5 · alien app
Out-of-distribution validation (not Python, not SPA+API — Rails/Sidekiq or a coupled-pair app). Exit: §10's paper personas hold against a real foreign app.
M4 · open-source
Real name, docs, security model, the demo (bootstrap → plan → deploy → kill → resume, prebuilt image). v2 design issues: out-of-process providers, blue-green, canary, co-rolled groups.
13 / Review changelog

What each review round changed

  • Wedge corrected (Kamal proxy: false exists) → plan/apply + compose-native ZDD; Sidekick/Haloy/Uncloud acknowledged.
  • CUE demoted to internal; YAML user surface.
  • Strategy & Backup planes cut; coupling admitted; health given a single owner.
  • Safety turned into protocols: journal, epochs/fencing, lock authority, resume/abort, divergence status, audit.
  • Rollback scoped honestly; migration gate; per-role modes + ordering; verify for every role; day-2 specified.

rev 2 → rev 3 (generality audit)

  • §10 added: overfit decomposition, three paper personas, artifacts/heartbeat quarantined, M3.5 alien-validator milestone.

rev 3 → rev 4 (second review round: fresh-eyes + fix-verification)

  • "Source of truth" honesty: the compose file is the contract; yeet renders a per-release deployable and shows the delta; the injected set is closed and declared.
  • Readiness compilation rule: ready: is the single owner; http/exec compile to the container healthcheck (proxy-gating); log/heartbeat are non-proxied-role wait conditions; compose-file healthcheck adoption/override defined.
  • Service classes closed the migrate hole: roles / accessories / jobs; all release + job invocations run --no-deps; preflight asserts accessory liveness; bootstrap defined for first contact.
  • Plan fidelity contract: stated ranking (config > images > choreography > hooks); prebuilt-digest vs build-mode binding; drift set defined.
  • Proxy lifecycle owned: managed vs external; proxy apply; namespaced label injection with collision detection.
  • Migration-gate protocol: $YEET_RESULT_FILE convention, fail-safe default, gate extended to abort.
  • Schema fixes: per-service images (the audit's own missed overfit), drain as a real field, stop-start deleted, environments overlay, destroy/host retire.
  • Scope cut: multi-host execution deferred to M3 (protocol designed, executor later) — answering the "v1 is enormous" finding.
  • Journal concretized: path, format, fsync, GC, per-host fencing records.

rev 4 → rev 5 (generality & robustness hardening)

  • Traffic-shift protocol: join / drain / converged as the proxy-provider interface; drain-before-SIGTERM ordering (SIGTERM never races the proxy); drain valid on rolling roles as the connection-bleed window; sticky-session / version-skew precondition stated.
  • Render canonicalization: docker compose config is the substrate — the compose dialect is never re-implemented; render/plan diff canonical forms. Compose-surface added to risks (it was the biggest unlisted one).
  • Generality boundary stated (§10): anything describable as a compose app — and inside it, roles may map to multiple services (schema seam reserved, execution gated), moving the PHP-FPM pair from non-fit to designed. Headless (no-proxy) and host-port TCP/UDP personas added.
  • Resource-exclusivity rule: rolling requires overlap-capable resources; validate warns on device reservations for rolled roles; recreate is the exclusive-resource mode.
  • One mutation regime: every mutating verb locks, journals, and fences identically; fencing's check-then-act residue owned explicitly.
  • Rollback vs rotated secrets: hash-mismatch warning + --current-secrets; secrets-at-rest retention window noted in risks.
  • Loose ends closed: image transport declared (registry or save|load archive — the air-gap path); multi-arch digest note; host-scoped managed proxy (multi-app hosts); accessory "healthy" requires a healthcheck; ready: timing knobs; Swarm added to prior art; max_parallel designed into M3 fan-out.
  • Corpus-tested (17 in-house compose projects): proxy-in-compose named a first-class shape (it's an accessory — 5/17 ship Traefik inside the compose file); all-accessory apps legal; init specified as a rollability doctor that prints each service's exact compose delta; the generality claim stated precisely — universal deployability, conditional (physics-bound) zero-downtime.
