Every name Onebox derives outside your own workload containers now begins with
`onebox`. **There is no migration and no fallback.** Onebox does not look for
the old names, read from them, or remove them. If you deploy an upgraded
project to a host that still holds `ob_` volumes, **it starts the service on a
new, empty volume**. The old data is still on the host, but nothing uses it.

Do the steps below **before** the first deploy with the new version.

## What changes

| Resource | Before | After |
| --- | --- | --- |
| Managed service container | `shop-postgres-1` | `onebox-postgres` |
| Restore-drill container | `shop-postgres-restore-1` | `onebox-postgres-restore` |
| Service and workload volumes | `ob_shop_postgres_data` | `onebox_postgres_data` |
| Service Compose project | `ob_shop_postgres` | `onebox_postgres` |
| Service network | `ob_shop` | `onebox_services` |
| Ingress network | `ob-ingress` | `onebox-ingress` |
| Workload containers | `shop-web-1` | unchanged |
| Application network | `shop_default` | unchanged |

Names in the `onebox` namespace no longer carry the application. Application
names may no longer be `onebox` or begin with `onebox-`, and a service may not
be called `proxy`, `discovery` or `services`.

## What the next deploy does without these steps

- **Unprotected services start empty.** A service without `backup` starts on a
  new, empty volume, uses the existing credential, and reports healthy. Your
  application connects to an empty database.
- **Protected PostgreSQL refuses to apply.** A service with `backup` records its
  cluster identity, so the deploy stops with `data volume
  onebox_<service>_data is missing`. Nothing is started.
- **The old service containers keep running.** They belong to the old Compose
  project, so the deploy does not replace them. They keep the old volumes open.
- **Routing stops until the workloads are redeployed.** The proxy moves to
  `onebox-ingress`, and each workload moves when it is next rolled.

## Move the data

Run this on the host as root. Set `APP` to your application name. The commands
stop the application, so plan for downtime. Copying the volumes temporarily
doubles the disk space they use.

1. Upgrade `ob` on your machine, but do not deploy yet.

2. On the host, remove the old service containers and stop the workloads:

   ```sh
   APP=shop
   docker ps -aq --filter label=ob.app=$APP --filter label=ob.service | xargs -r docker rm -f
   docker ps -q --filter label=ob.app=$APP | xargs -r docker stop
   ```

   Removing the service containers does not remove their volumes.

3. Copy every `ob_<app>_` volume into its `onebox_` name, keeping the labels
   Onebox uses to recognise it as its own:

   ```sh
   for old in $(docker volume ls -q --filter label=ob.app=$APP | grep '^ob_'); do
     new="onebox_${old#ob_${APP}_}"
     labels=$(docker volume inspect -f '{{range $k, $v := .Labels}}{{if or (eq $k "ob.app") (eq $k "ob.service")}}--label {{$k}}={{$v}} {{end}}{{end}}' "$old")
     docker volume create $labels "$new"
     docker run --rm -v "$old":/from:ro -v "$new":/to alpine cp -a /from/. /to/
   done
   ```

   A volume without the `ob.app` label is refused by preflight as a resource
   Onebox does not own. The loop copies the label, so the new volume passes.

4. Deploy from your machine:

   ```sh
   ob deploy production
   ```

   A protected PostgreSQL service checks that the copied volume holds the same
   cluster it recorded. If the copy is incomplete, the deploy stops here.

5. Check that the application sees its data. Then remove what the old names
   left behind:

   ```sh
   docker volume ls -q --filter label=ob.app=$APP | grep '^ob_' | xargs -r docker volume rm
   docker network rm ob_$APP ob-ingress
   ```

   `docker network rm` fails while anything is still attached to the network.
   Leave the old volumes in place until you are sure. They are the only copy
   of the data from before the upgrade.

## If you already deployed

If the deploy already ran, the old volumes are untouched. Stop the application
as in step 2, and remove the new empty volumes with `docker volume rm` after
checking that they hold nothing you need. Then continue from step 3.
