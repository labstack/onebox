<Section eyebrow="The contract">

## Bring a repository, one server, and approval.

Get structured observation, constrained change proposals, and evidence-backed execution inside a declared safety envelope. Onebox connects over SSH with known-host checking — there is no deployment agent to install on the host.

<Lifecycle>

1. `ob validate` — **Declare**

   Read the project file, resolve every shorthand, contact nothing. What Onebox understood is printable with `ob canonical`, with the origin of each value beside it.

2. `ob plan` — **Observe and propose**

   Inspect the host, compare it to the declaration, and seal the result: the typed operation graph, exact config, host state, image digests and rendered Compose, bound together.

3. `ob approve` — **Confirm, locally**

   A tamper-evident confirmation covering that plan, target, inputs, risk, operator label and expiry. A changed or expired plan needs a new one. Migrations use the strong ceremony, where the operator types the release id.

4. `ob deploy` — **Execute under a lock**

   Health-gated rollout, traffic drain, verification, then a versioned release with an explicit predecessor. An interruption leaves a checkpoint that `ob resume` or `ob abort` reconciles.

</Lifecycle>

</Section>

<Section eyebrow="The authoring contract">

## You write the declaration. Onebox owns the runtime.

A Compose file you wrote cannot be the contract — it describes containers, not intent. Compose becomes an artifact Onebox generates, digest-bound into the plan, printable with `ob preview`, and permanently ejectable with `ob eject`.

<Contract>

```yaml
api_version: onebox.run/v1
app: shop
environments:
  production:
    server: root@203.0.113.10
image: ghcr.io/acme/shop:1.4.0
domain: shop.example.com
port: 3000
```

- `shop-web-1`

  The container, with a one-based replica ordinal that is never omitted.

- `shop_default`

  The application's own Compose network, and `ob_shop` for its services.

- `onebox-proxy`

  The managed Traefik proxy, and the static configuration written for it.

- `/var/lib/ob/shop/releases/<id>`

  The release layout, with `current`, `journal` and `services` beside it.

Those names are contract, not configuration: once a persistent resource exists its name cannot change without migration, and a foreign resource already holding a derived name is refused rather than adopted. [Every accepted field](/reference/project-file) is generated from the loader, so the reference cannot describe something the binary will not take.

</Contract>

</Section>

<Section eyebrow="What it refuses">

## Refusing is the feature.

A tool that guesses produces a container that starts and stores nothing durable, or a job that runs at nearly the right time. Onebox would rather fail while you can still read the file.

<Refusals>

- `at load`

  **A roll with nothing to gate on**

  `strategy: rolling` with no health check. A rolling workload cannot publish a host port either, because two replicas cannot hold the same port during a roll.

- `at load`

  **A cron whose meaning would change**

  A schedule Onebox cannot preserve exactly, rather than one approximated. A job that runs at nearly the right time is a job that ran at the wrong time.

- `at load`

  **A driver it cannot run**

  Eleven drivers are supported. A twelfth name is refused, because inventing an image from it produces a container that starts and stores nothing durable.

- `shorthand_and_workloads`

  **Two ways of saying the same thing**

  Top-level workload shorthand mixed with a `workloads` block. It would be ambiguous which workload the top-level fields describe, so neither reading is chosen.

- `host_owner_mismatch`

  **A second application on a claimed host**

  Ownership is recorded at bootstrap and checked by every mutating command. It is released only once nothing of the application remains — volumes gone, and the proxy too if Onebox managed it.

- `at plan`

  **A promise it cannot keep**

  A backup policy on a driver that cannot honour one, and a major version change a driver cannot perform in place — rather than replacing the container and leaving the data intact and unreachable.

</Refusals>

</Section>

<Section eyebrow="Supporting services">

## Declare a database. Onebox runs it.

<Services>

`postgres` `mysql` `mariadb` `redis` `valkey` `mongodb` `rabbitmq` `minio` `meilisearch` `clickhouse` `nats`

Declaring `services: {postgres: 17}` makes Onebox run it: the image, a durable volume, a health check, a credential generated on the server that never travels, and the connection details the application reads. Anything not on that list is refused rather than guessed at.

PostgreSQL is also the one driver whose `backup` policy is honoured today — continuous archiving to a repository you own, point-in-time restore, and a drill that proves recovery without touching the live service. [Back up a database](/guides/back-up-a-database) is the procedure.

</Services>

</Section>

<Section eyebrow="Limits">

## What it does not do today.

Published here rather than three clicks away, because a capability list that omits its gaps is how an operator ends up trusting a backup that was never taken.

<Limits>

- **Backups cover managed services, not workload volumes**

  A service declaring `backup` — PostgreSQL today — is archived off-host and restorable to a point in time. A workload's own volume is not, and `ob doctor` says so for every workload holding durable data, because silence there would read as approval.

- **`mongodb` runs a standalone server, not a replica set**

  An application needing change streams or multi-document transactions will connect, authenticate, and then fail — in its own logs, not in anything Onebox says.

- **One host, and no failover**

  Rolling deployment can avoid interruption while the box is healthy. It cannot make a failed physical host available. Recovery onto another host is a separate, evidence-backed workflow.

[Shipped vs proposed](/status/capabilities) is the full account: what the binary does today, and what the schema accepts but cannot yet execute.

</Limits>

</Section>

<Section eyebrow="Built to be driven">

## One interface, for people and agents.

Deterministic, composable in CI, easy to test, and calling one canonical operations service that owns every lifecycle decision.

<Closing>

Every finite machine result uses one envelope carrying a schema version, the command, an outcome, and exactly one of `data` or `error`. Errors are typed, and where honest guidance exists they carry one command in its exact role — diagnostic, next, or resolving. Mutations are idempotent under retry.

There is no MCP surface, and adding one would earn no safety: a read-only tool list constrains nothing when every mutation goes through the CLI anyway. Point an agent at the `ob` binary the way you would point it at `gh`.

There is also no generic `--force`. Each override grants exactly one capability and is named for it.

- `--break-lock`

  Break a stale application or host lock, after inspecting its holder.

- `--break-migration-gate`

  Abort past a closed migration gate you have judged safe.

- `--allow-destructive-mounts`

  Apply a service change that detaches or replaces a data volume.

- `--no-rollback`

  Leave a failed deploy in place instead of recovering it.

- `--redeploy`

  Replace workloads that a no-op deploy would otherwise leave alone.

</Closing>

</Section>
